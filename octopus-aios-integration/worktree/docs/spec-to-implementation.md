# Спецификация → план → реализация (локально, без Notion)

Короткий процесс для агентов и людей: зафиксировать требования, разбить на шаги, вести прогресс в репозитории. В Cursor Cloud для этого репо нет Notion — тот же процесс **целиком в Git**: markdown, чеклисты, ссылки на PR и тесты.

## Источник правды

Выберите один основной артефакт и не плодите дубликаты без ссылки:

| Вариант | Когда уместно |
|--------|----------------|
| Файл в репо (`docs/superpowers/specs/…`, `docs/plans/…`) | Норма для Immortal Swarm: версионируется, виден в PR |
| Issue / обсуждение на GitHub | Внешние стейкхолдеры, трекер |
| Текст в чате агента | Только как черновик; итог переносится в markdown в репо |

В шапке спека полезно явно указать: цель, нецели (out of scope), ограничения (офлайн-тесты, без Docker и т.д.).

## Шаг 1 — таблица требований

Для каждой фичи завести список строк вида:

- **ID** — короткий идентификатор (`M1`, `auth-01`)
- **Требование** — что должно быть правдой после мержа
- **Критерий приёмки** — как проверить (команда, сценарий, тест)
- **Зависимости** — другие ID или внешние сервисы
- **Статус** — todo / in_progress / done

Расширенная классификация (по желанию):

| Тип | Что записать |
|-----|----------------|
| Функциональные | Поведение API, CLI, сценарии пользователя |
| Нефункциональные | Латентность, безопасность, размер зависимостей |
| Критерии приёмки | Команды проверки, ожидаемый вывод, edge cases |
| Зависимости | Что должно быть смержено раньше |

Можно держать таблицу в том же файле, что и план, или в начале спека под `docs/superpowers/specs/`.

## Шаг 2 — план реализации

Черновик плана: [`docs/plans/`](plans/) — файл `docs/plans/<тема>.md` (латиница и дефисы в имени).

План должен содержать:

1. Контекст и ссылки на спеки/код (пути к файлам).
2. Упорядоченные шаги с оценкой риска (сеть, крипто, миграции данных).
3. Что **не** входит в объём (явный non-goals).
4. Команды верификации (`python3 -m pytest -v`, smoke CLI).

Длинные архитектурные планы по-прежнему уместны в [`docs/superpowers/plans/`](superpowers/plans/).

### Шаблон плана (скопировать в `docs/plans/<feature>.md`)

```markdown
# План: <название>

## Обзор
Кратко зачем и что меняется.

## Связанный спек
- Ссылка на файл/issue или вставка ключевых абзацев.

## Сводка требований
- …

## Технический подход
- Модули, точки расширения, совместимость с `MemoryPort` / CLI.

## Фазы и задачи
### Фаза 1 — …
- [ ] Задача A (acceptance: …)
- [ ] Задача B

### Фаза 2 — …
- [ ] …

## Риски и смягчение
| Риск | Митигация |
|------|-----------|
| … | … |

## Критерии готовности
- `python3 -m pytest -q` зелёный
- Документация: `README.md` / `AGENTS.md` при новых командах
```

## Шаг 3 — реализация и PR

- Один PR — одна согласованная тема; в описании PR — ссылка на план и на спек (`Relates-to: docs/plans/foo.md`).
- Пока работа не влита, обновлять план-файл в той же ветке.
- После мержа: при необходимости перенести «уроки» в `docs/superpowers/specs/` или в `AGENTS.md` / `README.md`.

## Шаг 4 — трекинг прогресса

- Чекбоксы `- [ ]` / `- [x]` в том же `docs/plans/...md`.
- Закрытие фазы = все чекбоксы фазы отмечены и тесты проходят.

## Шаг 5 — разбиение задач (паттерны)

| Паттерн | Когда |
|---------|--------|
| По компонентам | `swarm/memory/`, `node.py`, тесты, конфиг |
| Вертикальные срезы | Одна фича end-to-end (CLI → порт → адаптер) |
| По приоритету | P0 блокер, P1 важное, P2 nice-to-have |

## Верификация

Перед пометкой «готово»: прогнать заявленные тесты и зафиксировать результат в PR (или в чеклисте плана).
