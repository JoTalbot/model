# Координация параллельной работы над AIOS

> **Важно:** этот репозиторий изменяется с разных машин, людьми и разными ИИ-агентами. Несколько сессий могут работать параллельно. Неизвестные незакоммиченные изменения всегда считаются чужой активной работой, а не мусором.

Этот каталог хранит переносимый между машинами контекст разработки. Он дополняет Git, но не заменяет ветки, коммиты, code review и внешние средства координации.

## Источники истины

1. `AGENTS.md` — обязательные правила для всех агентов и контрибьюторов.
2. `coordination/PROJECT_CONTEXT.md` — краткий актуальный срез проекта, приоритеты, риски и ближайший следующий шаг.
3. `coordination/sessions/` — отдельный журнал каждой рабочей сессии; это основной handoff-контекст.
4. `coordination/claims/` — advisory-заявки на область работы для раннего обнаружения пересечений.
5. Git (`status`, ветки, коммиты и diff) — фактическое состояние кода.

Если документы расходятся с кодом или runtime, факты из кода/runtime имеют приоритет, а расхождение нужно записать в журнал сессии.

## Краткий формат общения

Перед выполнением агент кратко сообщает цель следующей группы действий. Во время работы публикует только
этапные статусы, а после — короткий результат и следующий шаг. Сырые логи/diff сохраняются в журнале или
артефакте и не перегружают чат, если оператор прямо их не запросил. Служебный индикатор инструмента не
нужно дублировать текстом. Ошибки описываются кратко, без вывода секретов.

## Обязательный старт каждой сессии

```bash
cd /root/AIOS
cat AGENTS.md
cat coordination/PROJECT_CONTEXT.md
git status --short
git branch --show-current
git log -5 --oneline --decorate
find coordination/claims -maxdepth 1 -type f ! -name README.md -print
```

Затем агент обязан:

1. Выполнить `git fetch --all --prune`, если сеть и права это позволяют.
2. Проверить, не занят ли тот же модуль в `coordination/claims/` и свежих журналах `coordination/sessions/`.
3. Создать **свой**, а не общий журнал по `SESSION_TEMPLATE.md`.
4. Для задачи с изменением кода создать claim-файл вида:
   `coordination/claims/<scope>--<session-id>.md`.
5. Записать исходный commit, ветку, машину, агента, цель, scope и уже существующие изменения.
6. На одной машине использовать отдельный clone/worktree для параллельных агентов. Не переключать ветку в общем грязном worktree.

Время в координационных файлах записывается в UTC в формате ISO 8601.

## Идентификатор сессии

Рекомендуемый формат:

```text
YYYYMMDDTHHMMSSZ-<machine>-<agent>-<short-task>
```

Пример:

```text
20260814T083800Z-aios-arena-project-audit
```

Имена должны быть короткими, ASCII-safe и уникальными. При риске совпадения добавьте 6–8 случайных символов.

## Жизненный цикл сессии

Допустимые статусы:

- `ACTIVE` — работа выполняется;
- `PAUSED` — можно продолжить позже, следующий шаг явно записан;
- `BLOCKED` — записан блокер и условие разблокировки;
- `DONE` — работа завершена и проверки записаны;
- `ABANDONED` — продолжать нельзя без повторной оценки.

Во время работы обновляйте **только собственный журнал** после каждого существенного рубежа. Перед остановкой обязательно укажите:

- что именно было изменено;
- какие файлы затронуты;
- что проверено и точные результаты;
- что не проверено;
- последний безопасный commit;
- незакоммиченные изменения;
- один конкретный следующий шаг;
- известные риски, решения и предположения.

`PROJECT_CONTEXT.md` обновляется только после значимой завершённой задачи или при смене общепроектного приоритета. Детали одной задачи должны оставаться в её журнале, чтобы уменьшать конфликты в общем файле.

## Claim-протокол

Claim — не блокировка файловой системы, а раннее предупреждение другим агентам. В claim укажите:

```markdown
# Claim: <scope>
- Session: `<session-id>`
- Status: `ACTIVE`
- Agent: `<agent>`
- Machine: `<machine>`
- Started UTC: `<timestamp>`
- Expected files: `<paths or glob>`
- Goal: `<one sentence>`
```

Правила:

1. Один claim-файл принадлежит одной сессии.
2. Не изменяйте чужой активный claim без явного handoff.
3. Если scope пересекается, остановитесь и разделите файлы/ответственность либо согласуйте последовательность.
4. После `DONE` удалите claim из рабочего дерева; исторический контекст остаётся в журнале и Git.
5. Claim становится видимым другой машине только после публикации через общий Git remote. Непубликованный claim не защищает от межмашинного конфликта.

## Git-правила при параллельной работе

- Никогда не выполнять `git reset --hard`, `git clean -fd`, массовый checkout/restore или удаление stash без явного разрешения владельца изменений.
- Не использовать `git add -A` и `git commit -a` в общем/грязном worktree. Добавлять только собственные пути: `git add -- <path...>`.
- Перед коммитом проверять:

  ```bash
  git status --short
  git diff --check
  git diff --cached --name-only
  git diff --cached
  ```

- Один коммит — одна задача. Не включать чужие изменения «заодно».
- Для внешних агентов использовать ветку `agent/<session-id>/<task>`; для автокодера сохраняется контракт `auto/v3/*` из `AGENTS.md`.
- Перед merge/rebase повторно читать свежие claims и `PROJECT_CONTEXT.md`.
- Не делать force-push общей ветки. Публикация в remote выполняется только при наличии полномочий.
- При конфликте не выбирать автоматически `ours/theirs`: сохранить обе стороны, разобраться по журналам и владельцам scope.

## Правила безопасности

В координационные документы запрещено помещать:

- приватные SSH-ключи, токены, пароли, cookies;
- значения из `.env`, credential stores и приватных runtime-файлов;
- персональные данные клиентов, содержимое звонков/чатов;
- полные дампы логов с чувствительными данными.

Разрешены только имена переменных, относительные пути, redacted-описания и ссылки на защищённое хранилище.

## Если агент аварийно остановился

Следующий агент:

1. Не продолжает работу вслепую.
2. Читает журнал остановившейся сессии, claim, `git status` и diff.
3. Помечает старую сессию `BLOCKED` или `ABANDONED` только при наличии полномочий и объяснения.
4. Создаёт собственную recovery-сессию со ссылкой на исходную.
5. Сначала воспроизводит последний записанный check, затем продолжает с указанного следующего шага.

## Минимальное определение завершения

Сессия не считается переданной или завершённой, пока её журнал не содержит:

- итоговый статус;
- краткое резюме;
- список изменённых файлов;
- результаты проверок;
- commit/branch либо явное указание, что изменения не закоммичены;
- следующий шаг или `нет`;
- оставшиеся риски/блокеры.
