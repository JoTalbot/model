# Octopus — План ускорения и удешевления swarm-памяти (CAS Pack+zstd)
Автор: Arena agent. Дата: 2026-05-30. Статус: ПЛАН (прод не менялся в этой сессии).
Приоритет (#11): ПАМЯТЬ > ЖИТЬ > УПРОЩЕНИЕ. Безопасность (#13): миграция — поэтапно, бэкап->шаг->проверка инварианта 3 копий->лог.

## 0. Зачем (проблема, подтверждённая замерами 2026-05-30)
Текущая память = "file-per-object": 20268 объектов, каждый отдельный файл локально + отдельный объект в S3 + отдельный PUT на EC2.
ЗАМЕРЫ (read-only, на копии, прод не тронут):
- Логических данных: 13.98 МБ. На диске (блоки 4 КБ): ~90 МБ -> **раздув 6.5x** (медиана объекта 252 байта < 1 блок).
- Конкатенация всех объектов: 13.98 МБ -> zstd-19 = **8.54 МБ** (коэф ~1.64x на этом наборе; на чистом тексте/JSON будет выше при росте).
- Распаковка всего пакета: **0.056 c** (мгновенно).
- БД: gossip_messages = 411k строк / 163 МБ (главный раздуватель), node_metrics растёт (dead tuples 7848), docker 4.5 ГБ reclaimable.

ВЫВОД: основная боль не в объёме данных (он мал), а в КОЛИЧЕСТВЕ операций (20k мелких PUT/файлов) и в БД/докер-мусоре.
Pack+zstd убирает 20k операций -> репликация/бэкап/восстановление в РАЗЫ быстрее и дешевле по числу запросов S3.

## 1. Целевая архитектура: CAS Packstore (как git packfiles)
Принцип: контентно-адресуемое хранилище (ref=sha256) остаётся источником правды, но физически объекты упаковываются.

### 1.1 Слои
- LOOSE (горячий слой записи): новые объекты пишутся как сейчас в memory_pool/<sha> (быстрая запись, без блокировок).
- PACK (холодный слой): периодически (gc/packer) loose-объекты сливаются в pack-файлы:
  * pack-XXXX.zst — конкатенация N объектов, сжатая zstd (frame-per-pack или multiframe).
  * pack-XXXX.idx — индекс: sha256 -> (pack_id, offset, length, uncompressed_length).
  Размер pack — целевой 8–64 МБ (баланс: дешёвая дельта-докачка vs мало объектов S3).
- INDEX (метаданные): таблица в Postgres pack_index(ref, pack_id, offset, length, ulen, created_at) — O(1) поиск.

### 1.2 Путь ЧТЕНИЯ (read)
1) ищем ref в LRU-кэше в памяти (горячие объекты) -> hit = наносекунды.
2) если loose-файл существует -> читаем напрямую.
3) иначе по pack_index: открыть pack (mmap), seek offset, zstd-decompress нужный диапазон.
   (zstd поддерживает покадровую распаковку; для произвольного доступа — frame-per-object внутри pack или dictionary).
Эффект: чтение горячих данных без обращения к 20k inode; меньше нагрузка на ФС.

### 1.3 Путь ЗАПИСИ (write) — без изменения семантики
- Запись остаётся loose (атомарно, как сейчас). Упаковка асинхронна (packer по таймеру), не на критическом пути.
- WORM/подписи/шифрование сохраняются: упаковываем УЖЕ финальные байты объекта; sha256 не меняется.

## 2. Репликация и бэкапы (главное ускорение)
СЕЙЧАС: replicator шлёт до 20k объектов поштучно (S3 PUT-на-объект; EC2 — HTTP-на-объект).
СТАНЕТ: дельта-синк ПАКЕТАМИ.
- На S3/EC2 заливаются pack-файлы + idx (десятки объектов вместо 20k). Меньше запросов = меньше денег и латентности.
- Дельта: реплицируются только НОВЫЕ pack-файлы (immutable, никогда не переписываются) + текущий "open" pack.
- Манифест MANIFEST.json (sha256 списка pack-ов + контрольные суммы) — одна точка верификации целостности всего стора.
- Восстановление: скачать pack-файлы (параллельно, многопоточно) + распаковать. Замер показал распаковку 14МБ за 0.056с.
- Инвариант "3 независимые копии" СОХРАНЯЕТСЯ и УСИЛИВАЕТСЯ: проверяем не 20k объектов, а N pack-хэшей (быстрее аудит).

## 3. Экономия места
- Локально: pack+zstd убирает раздув 4КБ-блоков (90МБ -> ~9МБ pack + небольшой loose-хвост). ~10x по реально занятому месту.
- S3/EC2: храним сжатые pack вместо 20k несжатых объектов -> меньше объёма и числа объектов (дешевле listing/PUT).
- БД (быстрые победы, независимо от pack):
  * gossip_messages: ввести retention (хранить N дней / M последних), затем VACUUM (FULL в окне). Оценка: -150 МБ.
  * node_metrics: retention + автоваккум tune. 
  * docker image prune: освободит ~4.5 ГБ.
  * pg log/ /var/log: logrotate + compress. -1...1.9 ГБ.

## 4. Ускорение "в разы" — где именно
- Репликация/бэкап: 20k операций -> десятки. Сетевых round-trip меньше на 2-3 порядка -> кратно быстрее.
- Аудит копий: сверка pack-хэшей вместо 20k ключей -> быстрее в десятки раз.
- Чтение горячих данных: LRU-кэш + pack mmap -> меньше IOPS, стабильнее latency.
- Восстановление (DR): параллельная докачка pack + быстрая распаковка.

## 5. Поэтапный РОАДМАП (каждый шаг обратим, прод защищён)
Поток P (Packstore) — независим от потоков чистки БД/докера.
- P0. Прототип packer на КОПИИ (вне прода): собрать pack+idx из текущих 20k, проверить round-trip (sha совпадают 100%). [измерено частично]
- P1. Таблица pack_index + packer-скрипт (loose->pack), запуск в DRY-RUN (только пишет pack, loose НЕ удаляет). Verify.
- P2. Reader с фоллбэком: read(ref) = cache -> loose -> pack. Включить как ДОПОЛНИТЕЛЬНЫЙ путь чтения. Прогнать smoke/restore-drill.
- P3. Pack-aware репликатор: заливать pack+idx+MANIFEST на S3 и EC2 ПАРАЛЛЕЛЬНО со старым (двойная запись), сверить.
- P4. Переключить аудит/restore-drill на pack-манифест. Подтвердить инвариант 3 копий на pack-уровне.
- P5. Включить GC loose-объектов, которые уже в pack И в 3 копиях (никогда не удалять без подтверждения 3 копий). 
- P6. Старый file-per-object путь оставить как fallback ≥1 неделю, затем архивировать.

Поток C (Cleanup, быстрые победы, можно сразу в отдельной сессии по команде):
- C1. gossip_messages retention + VACUUM (окно). 
- C2. node_metrics retention.
- C3. docker image prune -a (только неиспользуемые). 
- C4. logrotate/gzip для /var/log.

## 6. Риски и защита (#13)
- НИКОГДА не удалять loose-объект, пока он не в pack И не подтверждён в 3 независимых копиях (local pack + AWS S3 + AWS EC2).
- pack-файлы IMMUTABLE (append-only). Манифест с криптоконтролем целостности.
- Каждый шаг: бэкап -> применить на dry-run -> проверить smoke+restore-drill+coverage=1.0 -> лог. Откат = выключить новый путь.
- Миграция формата (P-поток) — ТОЛЬКО в change-window по пошаговой команде пользователя.

## 7. Ожидаемый результат (оценка)
- Локальное место памяти: ~90 МБ -> ~9-12 МБ (вкл. loose-хвост). 
- Объектов в S3/EC2: 20k -> десятки. Время полной репликации: минуты/таймауты -> секунды.
- Время аудита/восстановления: кратно меньше. Стоимость S3-операций: значительно ниже.
- БД+докер быстрые победы: освобождение ~5-6 ГБ диска независимо от pack.
